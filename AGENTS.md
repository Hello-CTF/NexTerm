# NexTerm Agent Guide

Reply in the same language as the user.

Keep this file limited to hot-path rules: the project map, hard constraints, quality gates, and workflow requirements - things every task needs to know.

## Working Principles

- Code, not documentation, is the source of truth. Read the relevant code before every edit; never edit blind from memory or guesswork.
- Code first: deliver working code, keep explanations to the necessary minimum. Minimal implementation: no over-engineering, no single-use abstractions, no speculative features, no general-purpose layers without a current caller.
- Keep changes focused; do not slip in unrelated refactors.
- Commits and PRs carry no agent attribution or identity (no co-author, no "generated by" wording).
- Reviews state only problems and their fixes; debugging states evidence, location, and fix in one pass. If the cause is unknown, write "cause not identified" - never guess or fabricate an explanation.
- Punctuation in all output: half-width hyphen `-` and straight quotes `"` `'`; no em/en dashes, curly quotes, or decorative Unicode. Use CJK text when needed; code, commands, and paths must stay safe to copy-paste.
- Terminology: "mobile" covers Android, iOS, and iPadOS as one family by default; name a specific platform only for genuinely platform-specific matters (e.g. a display problem on one OS).

## Project Map

- `cmd/nexterm-desktop`: Wails v3 desktop app (Windows/macOS/Linux; mobile projects under `build/`).
- `cmd/nexterm-server`: Linux server for browser mode (multi-user accounts, server-side workspaces).
- `cmd/nexterm-agent`: device agent installed on managed hosts.
- `internal/session`, `internal/terminal`, `internal/pty`, `internal/supervisor`, `internal/transport/{base,ssh,winrm,local,device}`: the terminal/session stack; SSH sessions are daemonized and re-attachable.
- `internal/server`, `internal/account`, `internal/sync`: browser-mode HTTP server, account system, end-to-end encrypted asset sync.
- `internal/ai/`: AI assistant (agent loop, tools, guard, memory, providers, cron).
- `internal/fleet/{server,agent}`, `internal/deviceproto`, `internal/fleet/agent/purpose`: device enrollment, heartbeat, metrics, remote terminal; the device bridge wire protocol and the agent-side file/dial purpose servers.
- `internal/store`, `internal/db`, `internal/vault`, `internal/keys`, `internal/biometric`: GORM data layer, encrypted credential vault, OS keychain / biometric unlock.
- `internal/sharing`, `internal/update`, `internal/forward`, `internal/mount`, `internal/docker`, `internal/fs`: host sharing and public preview links, desktop auto-update, port forwarding, remote mounts, Docker management, file services.
- `src/`: React 19 frontend; `src/ipc/bindings/**` is wails3-generated (see "Generated bindings").
- `scripts/`: quality-gate scripts and `build.mjs` (frontend build, bindings check, reproducibility check).
- `website/`: GitHub Pages site. `lazycat/`: Lazycat package. `build/`: Wails build config plus Android/iOS projects. `deploy/systemd/`: server unit files.

Toolchain: Go 1.26, Node 24+, pnpm.

## Branch, Release, Versioning

- `master` is the only working and release baseline: branches are cut from the latest `master` commit and merged back via PR; Pages deploys on `master` push. Pushes to `master` are fast-forward only, after review with all gates green; no unreviewed pushes, no force pushes.
- Releases are `v*` tags pushed from `master`. The tag is the only version source: `wails.json`, `package.json`, and `lazycat/package.yml` always hold `0.0.0`; tag CI resolves `NEXTERM_RELEASE_VERSION` from the ref and stamps it into binaries and the dist manifest (master/PR builds keep the placeholder; local and Lazycat builds get a real version via `NEXTERM_RELEASE_VERSION` or by sitting exactly on a tag). The release workflow reuses the green CI run of the same tag at the same SHA (`CI_REUSE_EXPECTED_REF`).
- Tag CI may reuse same-SHA green master results for `quality`/`frontend-quality`/`postgres`, but all versioned frontend/native/mobile artifacts are rebuilt fresh - master's `0.0.0` artifacts are never reused, and `frontend-dist` comes only from the `frontend` job.
- The Windows Wails/NSIS exact-key cache on the default branch only speeds up release builds; version and evidence requirements are unchanged.
- Optional macOS signing: repo variable `NEXTERM_MACOS_SIGNING=true` plus `NEXTERM_MACOS_P12_BASE64`/`NEXTERM_MACOS_P12_PASSWORD` (secrets) and `NEXTERM_MACOS_SIGN_IDENTITY` (variable) signs with hardened runtime + timestamp; adding `NEXTERM_MACOS_NOTARY_KEY_BASE64` (secret) and `NEXTERM_MACOS_NOTARY_KEY_ID`/`NEXTERM_MACOS_NOTARY_ISSUER` (variables) enables notarization + stapling. Without these, distribution stays ad-hoc; notarization requires a Developer ID certificate.

## Coding Rules

- Comments are written in English. Default to no explanatory comments; code explains itself, and review-archaeology or provenance comments are never kept. Only functional directives are preserved, verbatim:
  - Go: `//go:build` (always line 1 of the file) and `//go:embed` (`cmd/nexterm-desktop/assets_production.go`).
  - Shebang (`#!...`) on line 1 of scripts.
  - Packaging directives `#@build if/else/end` in `lazycat/lzc-manifest.yml` (parsed by lzc-cli and `scripts/verify-manifest-injects`).
  - Frontend test line-1 pragma `/** @vitest-environment jsdom */`.
- Content inside string literals, templates, and heredocs (including pseudo-comments) is data - no cleanup may touch it.
- Platform branches use file-level `//go:build` on line 1 (common constraints: `windows`, `unix`, `darwin || linux`, `!windows`); name files after constraint semantics, not rigid suffixes. Non-platform tags: `production` (embeds desktop assets, requires `cmd/nexterm-desktop/dist`) and `race`. Run the matching `-tags` tests after changing tagged code.
- Small duplication beats premature abstraction: similar code stays duplicated until its third occurrence. Single-parameter internal methods are not turned into options objects. Functions split only along abstraction levels; wrappers that add no new level (especially single-call-site ones) are inlined, not extracted.
- No gratuitous docstrings or type annotations; no error handling for impossible branches - states guaranteed by the caller or excluded by the type system are not defended.
- Tests go into the module's existing test file first; new test files are not created lightly. When tests fail because of an intended behavior change, fix the tests first; change the implementation only for a real bug.
- Data layer is GORM + GORM Gen: models in `internal/store/model/`, generated queries in `internal/store/query/*.gen.go` (no hand edits; regenerate with `go run ./scripts/gen-gorm` and commit with the change). Schema comes from `Store.migrate` AutoMigrate at startup - no SQL migration files, no old-database compatibility; a legacy SQLite database containing `schema_migrations` is renamed to `<db>.legacy-<timestamp>` (including -wal/-shm sidecars) on open and started fresh. Business queries go through `query.Use(db).<Model>`; a missing record is `errors.Is(err, gorm.ErrRecordNotFound)`. SQLite via the pure-Go `github.com/glebarez/sqlite`; PostgreSQL via `gorm.io/driver/postgres`; the same models and query code serve both dialects.

## Generated Bindings

- `src/ipc/bindings/**` is wails3-generated; hand edits are forbidden and drift is rejected by the gate.
- Update intentionally with `wails3 generate bindings -ts -i -d src/ipc/bindings ./cmd/nexterm-desktop` (`task bindings`), committed together with the IPC change. Verify with `node scripts/build.mjs bindings`.

## Quality Gates and Test Cadence

Must be all green before committing; CI runs the same set:

- Go: `gofmt -l ./cmd ./internal ./scripts` (no output), `go vet -mod=readonly ./...`, `go test -mod=readonly ./...`.
- Frontend: `pnpm typecheck`, `pnpm lint`, `pnpm test`.
- Reproducible artifacts: `node scripts/build.mjs frontend --repro-check`.
- Static contracts: `go run ./scripts/verify-manifest-injects`; `SOURCE_DATE_EPOCH=1 go run ./scripts/check-reuse-wiring`; `go run ./scripts/check-conflict-columns`.
- `task check` runs the routine set in one go (`verify-manifest-injects` included; the wiring check is not - run `task verify:wiring` when those files change). `-race` and `-tags production` are in neither `task check` nor CI; run the corresponding `go test` locally for concurrency or production-tag changes.
- Cadence: focused tests during implementation (related Go packages / frontend tests plus `pnpm typecheck` and `pnpm lint`); high-risk changes (concurrency, protocols, persistence, security, database) immediately add integration tests and `go test -race ./...`; after a large task is integrated and rebased, one full `task check` + `task verify` on the final tree (verify = all gates plus a reproducible host desktop production binary build; it does not run a native WebView smoke). When producing release artifacts, `node .github/scripts/release-evidence.mjs <artifact dir>` validates the set and generates `SHA256SUMS`.
- PostgreSQL-gated tests (`internal/dbtest`, `internal/store`, `internal/account`, `internal/sync`, `internal/ai/cron`, `internal/fleet/server`) read `NEXTERM_TEST_PG_DSN` through the `internal/dbtest` harness; when unset each test SKIPs, and SKIP never counts as verified. Local rerun: `NEXTERM_TEST_PG_DSN='<dsn>' task test:pg`. The CI `postgres` job runs them against a real server and fails on any harness SKIP in the log; the DSN is masked via `add-mask`. Adding a gated package means updating the harness, the CI postgres job, and this bullet together.

## Session State Hot Paths

- Status-bar accounting: `connected` counts sessions with `status === "connected"`; among them, sessions with empty `tabs` and `kind !== "remote"` count separately as "idle". `tabs` is maintained by the backend in real time; the frontend refreshes via `resyncSessions({ silent: true })` and never guesses locally.
- Every `terminalApi.closeTab` call site (single close, batch, background-session process end, Docker exec cleanup) must call `resyncSessions({ silent: true })` when done; missing ones are rejected by the static guard `src/test/features/closeTabResync.test.ts`.
- Destructive kill selections require an `ask` warning; `detach` (move to background) is reversible and needs no confirmation; a saved "close directly" preference skips confirmation and can be changed back in settings.

## Review Rules

- Enumerate behavior changes, not just bugs: any input that worked before the change (config options, env vars, CLI arguments, request shapes, data written by old versions) must behave identically after it, unless the PR declares otherwise. For every removed or narrowed branch, answer "who used to reach here, and where do they go now".
- Replacements and ports carry the old path's feature inventory: supported inputs, fallbacks, defaults, and where each one went. A silently dropped item is a regression, not a cleanup.
- Silent failure outranks a crash: ignored configuration, skipped operations, or dropped data without a signal is the most severe finding.
- AI prompt wording is behavior: system prompts and tool descriptions under `internal/ai` affect every session; the PR names the blast radius and who takes over the dropped constraints.
- Contract surfaces are tripwires: changes to `src/ipc/bindings`, `.github/release-template.md`, workflow reuse wiring, or manifest injects must name the consumers and the compatibility strategy.
- Reviewers actually run the gates and verify behavior; approvals based on reports alone are invalid.

## Commit and PR Conventions

- PR titles and commit messages use Conventional Commits: `feat` / `fix` / `docs` / `refactor` / `test` / `ci` / `build` / `perf` / `chore`, with optional scope (e.g. `fix(fleet): ...`).
- PR descriptions answer three things: what problem it solves, what changed, how it was verified. User-perceivable changes are stated (release-notes material), and behavior changes are named explicitly - breaking changes are allowed, but dropped behavior and its blast radius must be spelled out. No hollow template text; the author can explain the change and its boundaries to the reviewer.
- No scratch in the repo: notes, handoffs, prototypes, and mockups are not committed; scratch goes to `.tmp/` (gitignored). Check `git status` and `git diff --staged --stat` before committing. Commits never introduce real secrets or personal information; the synthetic Slack token in `internal/ai/memory/redact_test.go` is an approved test fixture whose value is never printed into docs or logs.

## Multi-agent Collaboration

- Agent scopes never overlap - one file is never assigned to two agents. Dependencies are ordered explicitly; only independent work parallelizes.
- Implementation and review are separate agents; authors never review their own work. Rebase onto the latest `master` before implementing, and once more before the single final integration.
- Parallel work does not bypass the quality gates or the no-hand-edit rule for generated code.

## pprof Debugging

- Off by default in all three processes; enable on demand via flag (wins) or the shared `NEXTERM_PPROF_ADDR`: `nexterm-server --pprof-addr 127.0.0.1:6060`, `nexterm-desktop --pprof-addr 127.0.0.1:6061`, `nexterm-agent run -pprof-addr 127.0.0.1:6062`. Loopback only (a bare `:6060` binds 127.0.0.1); pass `0.0.0.0` explicitly when external access is truly needed - other non-loopback addresses are rejected. Block/mutex profile sampling rate is 1 when enabled.
- Capturing a hang: `curl -o goroutine.txt 'http://127.0.0.1:6060/debug/pprof/goroutine?debug=2'`; `go tool pprof 'http://127.0.0.1:6060/debug/pprof/profile?seconds=30'`; `curl -o trace.out 'http://127.0.0.1:6060/debug/pprof/trace?seconds=5'`.
