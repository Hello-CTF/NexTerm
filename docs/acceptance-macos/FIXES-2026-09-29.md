## 一、P0 传输层按行裁剪，结构化数据被静默砍掉

### 问题
`transport/mod.rs` 的 `cap_text`（400 行 / 120KB，§6.3 的**模型输入预算**）被放在了
`Transport::exec` 的必经路径上。`docker image --format '{{json .}}'` 这类**结构化**输出
一并被砍 —— 实机 `docker images` 569 行，容器面板显示「镜像 400」，**UI 无任何提示**。

根因有两条，缺一不可：
1. 裁剪位置错：预算约束是「喂模型」的需求，却被施加到了「通用取数」上；
2. `ExecResult.truncated` 被 `docker/cli.rs::docker_exec` 丢掉，所以连「被截断了」都看不见。

### 改法
- **裁剪上移到消费侧**。`Transport::exec` 三个实现（ssh / local / winrm）全部返回**原始输出**，
  不再调 `cap_text`；`ExecResult` 的文档写清这条硬约束（`stdout/stderr` 未裁剪）。
- 需要守预算的两处自己 cap：`ai::tools::server` 的 `exec_commands` / `search_files`
  工具、`ai::context::recon_snapshot`。AI 侧行为与从前**逐条一致**（同样是 400 行口径）。
- `truncated` 语义收敛为**原始字节硬熔断**（SSH 8MB / 本地 4MB）：以前是静默丢弃，
  现在触顶会置位，`docker_exec` 记一条 `tracing::warn`。

### 证据
| 项 | 结果 |
|---|---|
| 真机端到端 | 容器面板 **`镜像 569`**，与靶机 `docker images --format '{{json .}}' \| wc -l` = **569** 完全一致（修复前 400） |
| 真机端到端 | 镜像页渲染出全部条目，末条 `probius/rce_labs:v1`（修复前该页只有 400 行且无提示） |
| 单测守门 | 新增 `transport::tests::local_exec_keeps_full_output`：跑 `seq 1 1500`，断言 1500 行**不被裁**、无「已截断」标记。裁剪一旦挪回 `exec`，此用例立刻红 |
| 单测守门 | 新增 `transport::tests::cap_text_bounds_before_model`：确认预算裁剪本身没被删掉，只是换了位置 |

证据图：`21-fix-docker-images-569.png`

## 二、P1 后端错误渲染成 `[object Object]`

### 问题
内核 `AppError` 跨 IPC 序列化为 `{ code, message }` **对象**，而界面有约 30 处直接
`String(e)` / `JSON.stringify(e)` / `(e as Error).message ?? e`。项目里本来就有
`describeError()`（`ui/errorText.ts`，注释里明写「直接 `String(e)` 只会得到 `[object Object]`」）
且已用了 44 处，但仍有漏网 —— 磁盘挂载失败时那句 `挂载失败: [object Object]` 就是它。

### 改法
按文件逐条替换为 `describeError(e)`，共 **14 个文件 / 30 处**（含 `ipc/commands.ts` 的
`toAppError` 兜底，以及 `store.ts` / `TakeoverBanner.tsx` 里自写的
`typeof e === "object" ? JSON.stringify(e) : String(e)`）。

替换用脚本做**精确子串 + 命中数校验**（`/tmp/unify_error_text.py`，dry-run 先过一遍），
期望数与实际数不符直接失败，避免「看起来都改了」。

### 证据
| 项 | 结果 |
|---|---|
| 静态 | `pnpm typecheck` ✅ / `pnpm lint`（`--max-warnings 0`）✅ |
| 覆盖 | `grep -rn 'String(e)\|String(e2)\|String(err)\|JSON.stringify(e)' src` → **残留 0 处**（只剩 `ui/errorText.ts` 自身实现） |
| 覆盖 | 本轮替换 30 处 / 15 个文件；全仓现有 `describeError(` 调用 **80 处 / 22 个文件** |

## 三、P2-① 失败的挂载 / 断开动作不落审计

### 问题
`commands/mount.rs`：
- `mount_create` 只在**成功**后写审计，失败被 `?` 直接抛走 → 审计里只有成功的勾；
- `mount_remove` **一条都不写**，`state` 被 `let _ = state;` 丢掉。

挂载是「改变本机状态」的动作，成没成都得对得上账。

### 改法
- 抽 `mount_create_inner` / `mount_remove_inner`（校验 → 执行 → **成败都 audit**），
  命令壳只负责从 `ManagedState` 取 `Store`。抽出来的直接好处：测试能用
  `Store::open_in_memory()` 跑完整条路径，不用构造 Tauri `State`。
- 卸载新增可选 `sessionId`，只用于审计归属（老前端不传也能用）。
- 空参数在动审计之前就返回 —— 空参数不是「一次挂载尝试」，不该污染审计。

### 证据
| 项 | 结果 |
|---|---|
| 单测守门 | 新增 `commands::mount::tests::mac_mount_failure_is_audited`：断言 `exit_code=1` 恰好 1 条、`exit_code=0` 0 条、payload 含 `"ok":false` 且带上真实原因 `macFUSE` |
| 单测守门 | 新增 `commands::mount::tests::mac_unmount_failure_is_audited`（原来卸载一条都不记） |
| 单测守门 | 新增 `commands::mount::tests::empty_args_are_rejected_without_audit` |
| 未验证 | **没做界面端到端**：macOS 上入口已不可用，UI 走不到 `mount_create`。审计链路是逻辑级 + 单测验证 |

## 四、P2-② 侦察快照对容器名单有 `head -20` 硬上限

### 问题
`ai/context.rs` 的侦察命令写死 `docker ps ... | head -20`。本机恰好 20 个容器，
多一个就会**静默少给模型几条**，而模型会当成完整名单作答。

### 改法
改为 `head -60` 并**附上总数**：
```
== docker ps（总数 N）==
```
模型据此能自己判断名单是否完整。同时每条侦察命令的输出都过一遍 `cap_text`（裁剪上移后的
配套改动），真被裁掉会显式标注，不再无声。

### 证据
真机：靶机 20 个容器时输出含 `总数 20` 且名单齐全；60 行上限对应 3 倍余量，仍在 12k 字符
总预算内（`ai/context.rs` 外层的 `take(12_000)` 未变）。

## 五、P2-③ 挂载依赖没有预检 → 由「不可用标记 + 明确报错」取代

macOS 直接标记不可用（见下节）。Linux 侧补上原本缺失的两处：
- `sshfs` 用 `output()` 而非只 `spawn()`，**检查退出码**（原来退出码被丢，失败了也当成功）；
- `sshfs` 不存在时把裸 IO 错误（`No such file or directory`）翻译成
  `未找到 sshfs：请先安装（Debian/Ubuntu: apt install sshfs）`。

## 六、磁盘挂载在 macOS 标记为「暂不可用」

macOS 这条链路要 **macFUSE（系统扩展，需内核扩展授权 + 重启）+ sshfs** 两件外部依赖，
本轮适配未覆盖。原来的入口「点了必失败，且失败原因渲染成 `[object Object]`」——
修完 P1 后原因能看清了，但仍然是让用户白点一次。所以直接标成不可用。

### 三层实现（单一事实来源在 Rust）
| 层 | 位置 | 行为 |
|---|---|---|
| 事实来源 | `fs::mount::unavailable_reason()` | `cfg!(target_os = "macos")` → `Some("…依赖 macFUSE（系统扩展）+ sshfs，尚未完成适配")` |
| 前端能力 | `commands::mount_capability` 命令 → `app/capabilities.ts`（`main.tsx` 首帧前拉取） | 前端**不自己判断平台**，理由由内核下发；将来适配完成只改 Rust 一处 |
| 界面标记 | 图标栏 + 面板 | 图标置灰 + 右上角琥珀点 + tooltip「磁盘挂载（暂不可用）」；点击打开面板，面板顶部 `暂不可用` 徽标 + 「本平台暂不支持磁盘挂载」+ 原因 + 替代路径（文件树 / SFTP） |
| 硬防线 | `mount()` / `unmount()` | macOS 直接 `AppError::Unsupported`，绕过 UI 也拿不到「假装挂上了」的结果 |

`scan()` 保留（只读扫描真实挂载表，无副作用），不因标记不可用而篡改「列表 = 本机真实状态」这条铁律。

### 证据
| 项 | 结果 |
|---|---|
| 真机目视 | 图标栏第 6 个图标（磁盘）置灰 + 琥珀点；AX 树里 title = `磁盘挂载（暂不可用）` |
| 真机目视 | 点击后面板：`暂不可用` 徽标 + `本平台暂不支持磁盘挂载` + `磁盘挂载在 macOS 上暂不可用：依赖 macFUSE（系统扩展）+ sshfs，尚未完成适配`；挂载表单**完全不渲染**（AX 树查 `新建映射`/`本地盘符`/`强制重扫` 命中数 0） |
| 真机目视 | **无会话时同样可见**：`App.tsx` 的 `case "mount"` 原本是 `tab.sessionId ? <MountPanel/> : <EmptyState/>`，不可用时点进去是一片空白。已改为与「端口转发」同款的无条件渲染 |
| 单测守门 | `fs::mount::tests::mac_mount_is_explicitly_unavailable`：`mount()` / `unmount()` 均返回 `unsupported`，理由含 `macFUSE` |

证据图：`22-fix-rail-amber-dot.png`、`20-fix-mount-panel-unavailable.png`（有会话）、
`23-fix-mount-panel-no-session.png`（无会话）
